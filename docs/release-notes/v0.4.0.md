Sessions now refresh their tokens before they expire, and your app can read, exchange and decode
tokens, and change settings without a restart.

```
dotnet add package ThunderID.AspNetCore --version 0.4.0
```

Requires .NET 10. Implements the ThunderID SDK specification v0.9. Nothing is removed or renamed
from 0.3.0; see [One change in behaviour](#one-change-in-behaviour).

## What's new

- **Refresh ahead of expiry.** On each request with a session, tokens within
  `ThunderIDOptions.RefreshBeforeExpiry` of expiring (default 60 seconds) are refreshed and the
  cookie rewritten before your code runs. Requests that arrive together share one refresh, and a
  request that still carries the old cookie gets the new tokens instead of sending the old refresh
  token again, which ThunderID would treat as a replay.
- `HttpContext.GetThunderIDAccessTokenAsync()` returns the signed-in user's access token, refreshed
  first if due, or null without a session.
- `HttpContext.ExchangeThunderIDTokenAsync(request)` does an RFC 8693 token exchange, by default
  trading the user's access token for one whose audience is the `Resource` you name. The session's
  own tokens don't change. Typed request and result: `ThunderIDTokenExchangeRequest`,
  `ThunderIDTokenExchangeResult` and the `ThunderIDTokenTypes` constants.
- `ThunderIDJwt.DecodeUnverified(token)` reads a JWT's claims for display or logging. It verifies
  nothing, so never use it to authorize.
- `AddThunderID(IConfiguration)` reads the settings from a configuration section. When the
  configuration reloads, a new `ClientSecret`, `Scopes`, `Resource` or `RefreshBeforeExpiry`
  applies without a restart. A reload that changes `Authority` or `ClientId`, or has an invalid
  value, isn't applied at all, and a warning with its code is logged.
- 15 more codes in `ThunderIDErrorCodes`, 51 in all. 7 of the new ones are the JavaScript SDKs'
  codes for the same condition.

See [Tokens](https://github.com/pasindubalasooriya/thunderid-aspnetcore#tokens) and
[Changing settings without a restart](https://github.com/pasindubalasooriya/thunderid-aspnetcore#changing-settings-without-a-restart).

## One change in behaviour

**A session can now end when its refresh is refused.** In 0.3.0 nothing refreshed, so a session
kept its expired access token until the cookie expired. In 0.4.0, when ThunderID refuses the
refresh token (a 4xx, for example after the user's session was revoked at ThunderID), the cookie
is cleared and the request continues signed out, so a protected page sends the user to sign in. It
is logged as a warning with `JS-AUTH_CORE-RAT2-HE04`. When ThunderID can't be reached, the session
is kept and the next request tries again.

Refresh needs a refresh token, which ThunderID issues only when the app's grant types include
`refresh_token`. Without one, nothing changes from 0.3.0.

## Before you use it

- Token exchange needs `urn:ietf:params:oauth:grant-type:token-exchange` in the app's grant types,
  and a resource server registered for the `Resource` you name.
- One refresh per refresh token holds within one process. With more than one instance and no
  sticky sessions, two instances can refresh the same session at once, and ThunderID then ends it.
  See [Limits](https://github.com/pasindubalasooriya/thunderid-aspnetcore#limits).
- Back-channel logout needs ThunderID built from `main`; v1.1.0 doesn't include it.
