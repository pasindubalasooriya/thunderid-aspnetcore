Every error is now a `ThunderIDException` with a stable code, so your app can tell failures apart
without reading messages.

```
dotnet add package ThunderID.AspNetCore --version 0.3.0
```

Requires .NET 10. Implements the ThunderID SDK specification v0.8. **Breaking changes from 0.2.0**:
see [Migrating from 0.2](#migrating-from-02).

## What's new

- `ThunderIDException`, with `Code` and `Origin`, and two subtypes: `ThunderIDApiException` when
  ThunderID answered with an HTTP error (it adds `StatusCode` and `StatusText`), and
  `ThunderIDRuntimeException` for everything else. The original failure, when there is one, is the
  `InnerException`.
- `ThunderIDErrorCodes`: 36 codes, each documented. Where ThunderID's JavaScript SDKs have a code
  for the same condition, it's the same string.
- A failed sign-in callback carries a `ThunderIDException`: as `context.Failure` in your
  `OnRemoteFailure`, and as the `InnerException` of ASP.NET Core's `AuthenticationFailureException`
  otherwise. When ThunderID refused the authorization code, it has ThunderID's status.
- Invalid settings fail startup with one error that names every failed setting.
- `MapThunderIDBackchannelLogout` and `SignOutOfThunderIDAsync` used without `AddThunderID` fail
  with code `ASPNETCORE-CONFIG-REG-NF01`, which says to call `AddThunderID`.
- Sign-in parameters the SDK sets itself (`client_id`, `redirect_uri`, `code_challenge`,
  `code_challenge_method`, `state`) are ignored when you put them in
  `AdditionalAuthorizationParameters`, with a warning at startup naming them. In 0.2.0 sign-in
  threw an `ArgumentException`.
- Back-channel logout rejections are logged with their code.

See [Errors](https://github.com/pasindubalasooriya/thunderid-aspnetcore#errors) for every code and
where it reaches your code, and
[Protecting routes](https://github.com/pasindubalasooriya/thunderid-aspnetcore#protecting-routes)
for how ASP.NET Core authorization maps to the Express SDK's `protect()`.

## Migrating from 0.2

**`ThunderIDSignOutResult.RevocationError` is a `ThunderIDException?`**, not a `string?`.
`RevocationFailed` is unchanged.

```csharp
// 0.2
logger.LogWarning("Revocation failed: {Reason}", result.RevocationError);

// 0.3
if (result.RevocationError is { } error)
{
    logger.LogWarning(error, "Revocation failed ({Code})", error.Code);
}
```

**`LogoutTokenValidationResult.Error` is a `ThunderIDException?`**, not a `string?`. Its `Message`
is the reason 0.2 returned, and its `Code` says which check failed.

```csharp
// 0.2
string? reason = result.Error;

// 0.3
string? reason = result.Error?.Message;
string? code = result.Error?.Code;
```

**Startup errors are `ThunderIDRuntimeException`**, code `ASPNETCORE-CONFIG-VAL-IV01`. In 0.2 a
weakened setting threw `OptionsValidationException`, and a missing or `http` `Authority` or a
missing `ClientId` threw ASP.NET Core's own exceptions. The `OptionsValidationException` for a
weakened setting is now the `InnerException`. The message changed from lines starting
`ThunderID:` to one line starting `The ThunderID settings are invalid:`.

```csharp
// 0.2
catch (OptionsValidationException ex) { ... }

// 0.3
catch (ThunderIDException ex) when (ex.Code == ThunderIDErrorCodes.InvalidSettings) { ... }
```

**Argument errors are `ThunderIDRuntimeException`**:

| Call | 0.2 | 0.3 code |
|---|---|---|
| `AddScopePolicy(name)` with no scopes | `ArgumentException` | `ASPNETCORE-SCOPE_POLICY-ASP-IV01` |
| `new LogoutTokenValidator(...)` with no client ID | `ArgumentException` | `ASPNETCORE-LOGOUT_TOKEN-CTOR-IV01` |
| `new InMemoryLogoutSessionStore(retention)` with a retention that isn't positive | `ArgumentOutOfRangeException` | `ASPNETCORE-SESSION_STORE-CTOR-IV01` |

**The sign-in callback failure has one more level.** The `InnerException` of
`AuthenticationFailureException` (or `context.Failure` in `OnRemoteFailure`) is now the
`ThunderIDException`; what was there in 0.2, such as `OpenIdConnectProtocolException`, is its
`InnerException`.

```csharp
// 0.2
if (context.Failure is OpenIdConnectProtocolException) { ... }

// 0.3
if (context.Failure is ThunderIDException { Code: ThunderIDErrorCodes.SignInTokenRequestRejected }) { ... }
```

**Discovery failures are `ThunderIDException`.** An issuer mismatch, a discovery document or key
set that couldn't be fetched, or one ThunderID refused, is thrown as a `ThunderIDException`, with
IdentityModel's exception as the `InnerException` when there is one. In 0.2 each was an
`InvalidOperationException`, and `ThunderIDException` doesn't derive from it, so a
`catch (InvalidOperationException)` no longer catches them.

**Without `AddThunderID`**, `MapThunderIDBackchannelLogout` now throws when it's called, instead
of each request failing with "No service for type". `SignOutOfThunderIDAsync` throws the same
error.

**The back-channel logout `400` body changed for four cases.** 0.2 answered every lifetime failure
with the `error_description` `token is outside its lifetime`; 0.3 says `token has expired`,
`exp is missing` or `token is not valid yet` (a future `nbf`). A signing algorithm ThunderID
doesn't list was `signature is invalid` and is now `signing algorithm is not accepted`. ThunderID
doesn't read the body, so this matters only if you test against it.

**Log messages changed.** Back-channel rejections and revocation failures now include the code.
Update any alert that matches the 0.2 text.

## Before you use it

- Back-channel logout needs ThunderID built from `main`; v1.1.0 doesn't include it.
- See [Errors](https://github.com/pasindubalasooriya/thunderid-aspnetcore#errors) for the two
  limits on sign-in callback errors, and
  [Limits](https://github.com/pasindubalasooriya/thunderid-aspnetcore#limits).
